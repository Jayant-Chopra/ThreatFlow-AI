# ThreatFlow AI — Evaluation 1 Final Output Schema

## Status and scope

This document freezes the **external analyzer-output contract** for Evaluation 1.
It is the interface consumed by the backend and attack-graph components. Internal
AST, traversal, and program-model representations are deliberately not part of
this contract and may change without changing this schema.

Evaluation 1 analyzes JavaScript Node.js / Express projects using Babel Parser
and `@babel/traverse`. It extracts routes, functions, HTTP-input sources,
recognized sinks, variables, ID-based relationships, and basic source-to-sink
taint findings for these rules only:

- SQL Injection
- Command Injection
- Dangerous Code Execution (`eval` and `Function`)

The scan performs basic local data-flow only. TypeScript, languages other than
JavaScript, narratives or remediation generated by an LLM, advanced
interprocedural or chokepoint analysis, production auth/multi-user behavior,
advanced risk scoring, full JavaScript semantic execution, and fabricated/demo
findings are out of scope.

## Contract rules

- The result is one JSON object per scan and uses `schemaVersion: "1.0"`.
- Every top-level field below is required. Collection fields are arrays and are
  present even when empty.
- All IDs are strings unique only within that scan. They need not be globally
  persistent or stable between scans.
- `file` values are project-relative paths using `/` separators. `project.path`
  identifies the scanned project as supplied by the caller; it can be absolute.
- `line` values are one-based source line numbers. If a location cannot be
  determined, the extractor omits that optional object rather than emitting an
  invented location or finding.
- `relationships[].from` and `relationships[].to` always contain entity IDs
  found in this output, never a variable or function name. Names and expressions
  are display/evidence values only.
- `findings` contains only evidence-backed analyzer results. No synthetic demo
  findings are permitted in production analyzer output.

## Top-level shape

```json
{
  "schemaVersion": "1.0",
  "project": {
    "name": "example-api",
    "path": "C:/work/example-api"
  },
  "files": [],
  "routes": [],
  "functions": [],
  "sources": [],
  "sinks": [],
  "variables": [],
  "relationships": [],
  "findings": [],
  "summary": {
    "filesAnalyzed": 0,
    "routesFound": 0,
    "functionsFound": 0,
    "sourcesFound": 0,
    "sinksFound": 0,
    "findingsFound": 0
  }
}
```

`schemaVersion` is the contract version. `project.name` is the project display
name and `project.path` is the caller-supplied scan root. `summary` is a count
of the corresponding extracted collections: `files` (not only emitted file
objects), `routes`, `functions`, `sources`, `sinks`, and `findings`.

| Top-level field | Meaning |
| --- | --- |
| `schemaVersion` | Required contract version, currently `"1.0"`. |
| `project` | Scan-root identity object containing required string `name` and `path`. |
| `files` | Array of JavaScript files considered by the scan. |
| `routes` | Array of extracted Express route entities. |
| `functions` | Array of extracted function entities. |
| `sources` | Array of extracted HTTP-input source entities. |
| `sinks` | Array of recognized vulnerability sink entities. |
| `variables` | Array of tracked local data-flow variable entities. |
| `relationships` | Array of directed, ID-based graph edges between extracted entities. |
| `findings` | Array of evidence-backed vulnerability findings. |
| `summary` | Required count object with the six fields shown in the JSON shape. |

## Collection object shapes

### `files`

One object for each JavaScript file successfully considered by the scan.

```json
{
  "path": "controllers/userController.js",
  "language": "JavaScript"
}
```

`path` is unique within `files`. `language` is always `"JavaScript"` in
Evaluation 1. A file that cannot be parsed may still be represented here when
it was considered; no unsupported-language entries are produced.

### `routes`

```json
{
  "id": "route_001",
  "method": "GET",
  "path": "/users",
  "file": "routes/userRoutes.js",
  "line": 5,
  "handler": "getUsers"
}
```

`method` is the uppercase Express HTTP method. `path` is the route path literal
as written or resolved by the supported basic extraction; it is `null` when a
recognized route uses a dynamic path that Evaluation 1 cannot resolve. `handler`
is the source-level handler display name; it is not an ID and is `null` for an
anonymous or otherwise unresolvable handler. When a handler maps to a function,
that authoritative connection is represented with a `ROUTE_TO_FUNCTION`
relationship from this route ID to the function ID.

### `functions`

```json
{
  "id": "func_001",
  "name": "getUsers",
  "file": "controllers/userController.js",
  "line": 3
}
```

`name` is the extracted source-level function name. It is `null` when no
meaningful static name exists; anonymous functions must still have their own ID
but do not receive a fabricated display name.

### `sources`

```json
{
  "id": "source_001",
  "type": "HTTP_INPUT",
  "expression": "req.query.id",
  "file": "controllers/userController.js",
  "line": 5
}
```

Evaluation 1 emits `HTTP_INPUT` for statically identifiable accessed properties
of `req.query`, `req.params`, `req.body`, `req.headers`, and `req.cookies`.
Both property notation (for example, `req.query.id`) and a static bracket key
(for example, `req.query["id"]`) are supported. `expression` is a deterministic,
concise source-code representation for display and evidence.

### `sinks`

```json
{
  "id": "sink_001",
  "type": "DATABASE",
  "name": "db.query",
  "file": "controllers/userController.js",
  "line": 7
}
```

`type` identifies the sink family: `DATABASE`, `COMMAND_EXECUTION`, or
`DANGEROUS_CODE_EXECUTION`. `name` is the recognized callee or constructor
expression, for example `db.query`, `child_process.exec`, `eval`, or `Function`.
Sink call arguments and AST context are internal analyzer data for later taint
analysis and are not part of this external JSON contract. A sink denotes a
potentially dangerous operation, not a vulnerability finding by itself.

### `variables`

```json
{
  "id": "var_001",
  "name": "id",
  "file": "controllers/userController.js",
  "line": 5
}
```

Each object represents a tracked local binding or assignment target relevant to
the extracted basic data flow. `name` is not globally unique; use `id` to
disambiguate it. Evaluation 1 tracks direct declarations, identifier
assignments, and clean destructuring bindings; object-property writes are not
local variables. Binding/scope identity and assignment-node context remain
internal analyzer data so same-named variables in different scopes are not
merged.

### `relationships`

```json
{
  "from": "source_001",
  "to": "var_001",
  "type": "ASSIGNMENT"
}
```

`from` and `to` reference IDs from `routes`, `functions`, `sources`, `sinks`,
or `variables`. Evaluation 1 relationship types are:

- `ROUTE_TO_FUNCTION`: a route handler resolves to an extracted function
  binding in the same static scope or through a supported direct CommonJS
  `module.exports` / destructured `require(...)` link.
- `ASSIGNMENT`: a source expression is assigned to a tracked variable.
- `VARIABLE_TO_VARIABLE`: a tracked variable occurs in another tracked
  variable's direct initializer or identifier assignment.
- `DATA_FLOW`: a source or tracked variable occurs in a recognized sink
  argument.
- `FUNCTION_CALL`: reserved for a future reliably resolved direct call; it is
  not emitted by the Evaluation 1 model yet.

The directed edges are the graph integration surface. Consumers must use IDs to
join entities and must not infer entity identity from display names. These are
basic static/syntactic dependencies, not claims of complete runtime behavior.

### `findings`

```json
{
  "id": "finding_001",
  "type": "SQL_INJECTION",
  "severity": "HIGH",
  "title": "Potential SQL Injection",
  "file": "controllers/userController.js",
  "line": 7,
  "source": "req.query.id",
  "sink": "db.query",
  "route": "GET /users",
  "evidence": "req.query.id flows through id into db.query(...)"
}
```

`type` is one of `SQL_INJECTION`, `COMMAND_INJECTION`, or `CODE_EXECUTION`.
`severity` is `HIGH` for these initial taint
findings. `title` is a concise human-readable rule label. `source`, `sink`, and
`route` are human-readable evidence values (`route` is `METHOD path` when a
route association is available; otherwise it is `null`). `evidence`
is a short analyzer-derived explanation of the observed flow, not an LLM
narrative or remediation recommendation. The Evaluation 1 code-execution rule
is taint-only: constant `eval`/`Function` use is not emitted as a finding.

## Consumer expectations

The backend may render the collections directly, while the attack graph can use
the directed `relationships` edges plus the corresponding entity IDs. A finding
is associated with its underlying graph through the source-to-sink data-flow
relationships and matching source/sink evidence fields; the schema intentionally
does not expose internal AST node IDs or require stable IDs across scans.

Any additive field or changed meaning requires a schema-version decision before
it is emitted to external consumers.
